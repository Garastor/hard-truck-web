# 07. Реверс-інжиніринг `HTruck.exe`

**Мета:** зрозуміти, як працює оригінальний рушій (фізика вантажівки, колізії, ШІ, правила, камера),
щоб наша реалізація **поводилась так само**. Код з `.exe` ми **не копіюємо**: лише вивчаємо формули
та логіку і пишемо їх заново (див. [06](06-legal-and-risks.md#4-реверс-інжиніринг)).

## 1. Що вже відомо про `HTruck.exe` (первинний аналіз)

| Факт | Значення для нас |
|------|------------------|
| PE32 (x86), зібрано **6 квітня 1999**, 1.8 МБ; `HTruck.exe` в установці й на CD однакові | Одна версія, аналізуємо її |
| Секції `BEGTEXT` / `DGROUP`, лінкер 2.18 → **компілятор Watcom C/C++** | Watcom передає аргументи в регістрах (`EAX, EDX, EBX, ECX`), а не через стек → декомпілятору треба явно вказати цю домовленість (`__watcall`), інакше аргументи функцій «губляться» |
| Код **не стиснутий і не зашифрований** (секції мають нормальні розміри) | Аналізувати можна одразу, без розпаковування |
| Налагоджувальних символів (PDB) немає, експортується одна функція (`AuxWndProc`) | Імена функцій доведеться давати самим |
| **Є імена класів і методів у повідомленнях про помилки:** `_Car_V::run2`, `_Car_V:get_WheelsForces`, `_Car_V:check_damage`, `_Car_V:form_position1`, `_Vehicle`, `VEHICLE::make_new_Pos`, `_MovingBox::set_Box_Collision_Detail`, `_Viewer::attach_vehicle`, `TaskManager`, `CarWiper`, `_NetVehIn` | Чудові «якорі»: знайшовши рядок, знаходимо функцію, яка його використовує, тобто сам метод фізики |
| Ключі параметрів з `TRUCK.TCH` прямо в коді: `body_mass`, `gear_trans_coeff%d`, `driving_wheels`, `CenterMassInB3D`, `front_wheel_thickness`, `cargo_and_body_pick_load`, `center_of_cargo_bottom`, `friction_coeff`, `default_ASS_steering` | Через ці рядки знаходимо, **куди** читається кожен параметр, а звідти — **як** він використовується у фізиці |
| Апгрейди та економіка: `Forced engine`, `Super tyres`, `Adjustable air suspention`, `Not enough money` | Підтверджує, що в грі є гроші й тюнінг; знаходимо ціни та ефекти |
| `error.log`: `f2pi(): param too large -nan. _Car_V:run2` | Відомий збій фізики на сучасних ПК; ця функція — головний цикл симуляції авто |

## 3. Як Claude Code працюватиме з `.exe`

```
Ghidra (headless) ──pyghidra-mcp──► Claude Code
     │                                   │
     │ проєкт re/htruck.gpr              │ знаходить рядок "_Car_V:get_WheelsForces"
     │                                   │ → xref → декомпілює функцію
     │                                   │ → перейменовує змінні та поля структур
     ▼                                   ▼
re/notes/*.md  ◄──── висновки: формули, константи, порядок оновлення у кадрі
```

Налаштування (Фаза R0):
```bash
winget install EclipseAdoptium.Temurin.21.JDK
```
Далі завантажити Ghidra з https://github.com/NationalSecurityAgency/ghidra/releases, розпакувати в `C:\Tools\ghidra`,
встановити змінну `GHIDRA_INSTALL_DIR` і підключити MCP:
```bash
pip install pyghidra-mcp
```
```bash
claude mcp add ghidra -- pyghidra-mcp
```
(Точні параметри запуску звірити з README pyghidra-mcp на момент встановлення.)

Проєкт Ghidra та нотатки зберігаються в `re/` (у `.gitignore`: `re/*.gpr`, `re/*.rep`; нотатки `re/notes/*.md` можна комітити,
бо це наш опис поведінки, а не код гри).

### Критерій «фізика як в оригіналі»
Автотест у Vitest проганяє нашу симуляцію з тими самими вхідними даними, що й в еталонній телеметрії (R5/R8),
і перевіряє відхилення: швидкість ±5 %, гальмівний шлях ±5 %, радіус розвороту ±10 %.

## 5. Поради

- Починати з **рядків-якорів** (розділ 1): це найшвидший шлях від «тисячі безіменних функцій» до потрібної.
- Спершу **структура даних** (`_Car_V`), потім функції: коли поля названо, декомпільований код читається майже як вихідний.
- Числа з плаваючою комою (маса, коефіцієнти) часто лежать у `DGROUP` як константи: Ghidra показує їх як `float` / `double`.
- Кожну гіпотезу перевіряти **динамічно** (x32dbg/Cheat Engine): змінили значення в памʼяті → вантажівка повелась очікувано.
